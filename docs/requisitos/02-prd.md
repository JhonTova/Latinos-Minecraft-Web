## Notas del CTO sobre este requisito

### Valoración general

**Este documento es sustancialmente más útil que el 01.** El 01 define
aspiraciones; el 02 define *qué se construye*. Si hubiera que elegir uno solo,
sería este.

### Solapamiento con el Requisito 01

Secciones duplicadas entre ambos documentos:

| Sección | Doc 01 | Doc 02 |
|---|:---:|:---:|
| Objetivos corto/medio/largo plazo | ✔ | ✔ |
| Competencia + FODA | ✔ | ✔ |
| Monetización y planes | ✔ | ✔ |
| Riesgos + mitigación | ✔ | ✔ |
| Criterios de éxito / KPIs | ✔ | ✔ |
| Roadmap | ✔ | ✔ |
| Requisitos no funcionales | ✔ | ✔ |
| Tipos de cliente / usuarios | ✔ | ✔ |

≈ 40% de solapamiento. **Recomendación:** fusionar en un único documento
producto+estrategia. Mantener dos versiones de las mismas secciones garantiza
que se desincronicen.

### Contenido nuevo y valioso (no está en el 01)

1. **Organizaciones + membresía múltiple** — decisión estructural correcta (ver abajo)
2. **Sistema de roles y permisos granulares** — define el modelo de autorización
3. **Ciclo de vida del servidor** (registro → verificación → suspensión → transferencia)
4. **Listado de funcionalidades por módulo** — es el inventario real de pantallas
5. **User stories con criterios de aceptación** — convertible directamente en tareas
6. **Experiencia de usuario** (desktop/tablet/móvil, dark mode, accesibilidad)
7. **Flujo completo del voto** (descubrimiento → recompensa)

### Decisión que el CTO respalda explícitamente

**Organizaciones desde el día 1, en lugar de "un servidor = un dueño".**

Justificación: convertir un modelo mono-propietario en multi-tenant después
de tener usuarios reales exige migrar cada tabla que referencia al propietario,
reescribir toda la capa de autorización y migrar datos en producción.
Diseñarlo correctamente desde el inicio cuesta días; retrofitearlo cuesta meses.

Es, además, un requisito real: los networks de Minecraft se administran en
equipo (dueño, desarrollador, moderadores), no por una sola persona.

### Riesgos de alcance detectados

| Petición | Problema | Propuesta |
|---|---|---|
| "Genera absolutamente todos los casos de uso" | Un producto de este tamaño tiene 300-500 casos de uso. Inviable y nadie los lee. | 15-20 casos de uso críticos, con caminos de error. El resto emerge al implementar. |
| Marketplace + Subastas + Publicidad + Pagos en el PRD | Cuatro productos financieros independientes | Definirlos a nivel conceptual (1 página c/u), no especificarlos |
| "Versión Cloud" en el roadmap | La plataforma ya es SaaS en la nube; el término no aplica salvo que se refiera a self-hosted | Aclarar con el usuario qué significa |

### Pregunta abierta generada por este documento

El documento asume que la plataforma es **multi-tenant pública** (miles de
propietarios registran sus servidores). Esto confirma la interpretación SaaS
frente a la de "web para el servidor LatinosMC". Pendiente de confirmación
explícita del usuario.
